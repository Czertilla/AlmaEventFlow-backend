# ADR 0005. Запросы доступа, гранты и выгрузка (этап 3)

Дата: 2026-11-03. Статус: принято. Основа: основное ТЗ, разделы 5.1, 7, 8, 9, 10, 12; ТЗ-дополнение,
разделы 3.2, 4.2, 9.8; ADR 0001–0004.

## Контекст

После этапа 2 чувствительные поля видят только владелец и суперпользователь, и каждый такой доступ
журналируется. Руководителю коллектива для поездок, пропусков и договоров нужны данные участников.
Этап 3 даёт ему целевой доступ: руководитель создаёт запрос с комментарием, каждый участник отвечает
на свой грант, а выгрузка отдаёт только то, что открыли действующие гранты.

## Решения

**Таблицы.**
- `access_request`: кто просит (`grantee_person_id`, без FK), коллектив (`collective_id` и
  `collective_name`), `comment`, `expires_at`, `created_by_user_id`, `created_at`, `edited_at`.
- `access_request_field`: PK `(request_id, field_key)`.
- `access_grant`: `request_id` (FK, CASCADE), `subject_person_id` (FK на `person`, CASCADE),
  `status` (`varchar` с CHECK: `pending`, `active`, `declined`, `revoked`), `decided_at`, `revoked_at`,
  `consent_evidence` (JSONB, пока всегда пуст), `UNIQUE (request_id, subject_person_id)`.
- Индексы: `access_request (grantee_person_id)` и `access_grant (subject_person_id, status)`.
  Запросы по `request_id` обслуживает уникальный индекс.
- Запрос и его поля не меняются никогда: на обе таблицы повешены триггеры `append_only_guard()` на
  `UPDATE`, `DELETE` и `TRUNCATE`. Другой комментарий, срок или набор полей — только новым запросом.
- Статус `expired` не хранится. Он вычисляется при чтении (`grant_state`): `pending` или `active`
  после `expires_at`.

**RPC в event** (только чтение, событий не добавлено):
- `rpc.event.collective-principal-check`: `(person_id, collective_id)` →
  `{is_principal, name, is_verified}`.
- `rpc.event.collective-active-members`: `collective_id` → `person_ids`, только активные члены, без
  руководителя.
- Таймаут 2 с, без повторов и без кэша. Сбой или таймаут — `503 EVENT_SERVICE_UNAVAILABLE`.
- Взаимной аутентификации нет. Это прежнее решение владельца для всех RPC (ADR 0001).

**Создание запроса** (`POST /profile/v2/access-requests`, только подтверждённый аккаунт):
- поля — непустой список без повторов, только `grantable` и не устаревшие (`422 ACCESS_FIELD_NOT_GRANTABLE`);
- комментарий после trim от `COMMENT_MIN_LEN` до `COMMENT_MAX_LEN` символов (`422 ACCESS_COMMENT_LENGTH`);
- `expires_at` с часовым поясом, позже текущего момента и не дальше `GRANT_MAX_TTL_DAYS`
  (`422 ACCESS_EXPIRES_OUT_OF_RANGE`);
- вызывающий по своей связи в `profile` — руководитель коллектива по данным event
  (`403 NOT_COLLECTIVE_PRINCIPAL`), а коллектив подтверждён (`403 COLLECTIVE_NOT_VERIFIED`).

Гранты `pending` создаются для активных членов на момент запроса, кроме самого руководителя и людей,
которых `profile` не знает. Каждому субъекту уходит строка журнала `request_created` и уведомление:
кто просит, коллектив, поля, комментарий, срок. Пришедший в коллектив позже гранта не получает.

**Ответ субъекта** (`POST /profile/v2/grants/{id}/approve|decline|revoke`). Отвечает только человек,
для которого грант, через аккаунт, привязанный к нему в `profile`. Для всех остальных, суперпользователя
включительно, это `404 GRANT_NOT_FOUND`. Переходы:
- `approve`: `pending` → `active`. Запрос не истёк (`409 ACCESS_REQUEST_EXPIRED`), охлаждение после
  смены связи прошло (`409 GRANT_COOLDOWN`, `link_cooldown_left`);
- `decline`: `pending` → `declined`, в том числе после истечения;
- `revoke`: `active` → `revoked`;
- любой другой переход — `409 GRANT_STATE_CONFLICT`. Отозванный и отклонённый не восстанавливаются.

Грант блокируется (`FOR UPDATE`), решение пишется в журнал (`grant_approved`, `grant_declined`,
`grant_revoked`, `via=self`) в той же транзакции.

**Выгрузка** (`POST /profile/v2/access-requests/{id}/export`, тело `{fields?}`). Если одна из проверок
не прошла, вся выгрузка — отказ и строка `denied` без субъекта, с `request_id` и кодом причины:
1. Вызывающий — автор запроса (`404 ACCESS_REQUEST_NOT_FOUND`, `NOT_GRANTEE`).
2. Запрос не истёк (`409 ACCESS_REQUEST_EXPIRED`, `REQUEST_EXPIRED`).
3. Запрошенные поля входят в поля запроса (`422 ACCESS_FIELD_NOT_REQUESTED`, `FIELD_NOT_REQUESTED`).
4. Вызывающий сейчас руководитель подтверждённого коллектива (`403`, `NOT_PRINCIPAL`,
   `COLLECTIVE_NOT_VERIFIED`; при сбое event `503`, `EVENT_UNAVAILABLE`).
5. Состав коллектива сейчас (при сбое event `503`, `EVENT_UNAVAILABLE`).

Выгружаются субъекты с `active` грантом, которые сейчас активные члены. Остальные попадают в `skipped`
со статусом `pending`, `declined`, `revoked` или `not_member` (грант активен, но человек ушёл из
коллектива; для него пишется строка `denied` с `NOT_MEMBER`). Перед чтением активные гранты ещё раз
берутся с `FOR SHARE`, так что отзыв, пришедший во время выгрузки, её не пропускает.

В одной транзакции с выдачей пишутся:
- по строке журнала `export` (`via=grant`, `grant_id`) и по уведомлению на каждого выгруженного;
- строка `export` об операции целиком (без субъекта).

Ответ идёт с `Cache-Control: no-store`. Файлов на сервере нет: таблицу строит клиент.

**Формат выгрузки — записи по строкам** (решение владельца). У каждого выгруженного `records` — по
записи на хранимую строку: анкета, каждый контакт, каждый паспорт. Строка, продолжающая другую,
входит в её запись: вариант ФИО — в запись своего паспорта. Внутри записи ключ реестра → значение.
Поле из нескольких колонок отдаётся объектом колонок, ссылочное — названием (диета, группа).

**Общий читатель по реестру.** Выгрузка ничего не знает о паспортах и контактах:
- `Source(table, person | parent)` в реестре говорит, как строка таблицы связана с человеком;
- `Reference(table, label)` у колонки говорит, чем показывать id;
- `RegistryRowsRepo` читает любые колонки по этим описаниям;
- `PersonalDataService._read_fields` расшифровывает строки и собирает записи;
- `validate_registry()` при старте проверяет источники, ссылки и что поле, которое можно запрашивать,
  лежит в одной таблице.

Поле, зарегистрированное в тестовой фикстуре вместе со своим источником, проходит весь путь: запрос,
согласие, выгрузку, журнал и уведомление.

**Журнал субъекта.** `GET /profile/v2/access-log/my` показывает комментарий и название коллектива
для записей с `request_id`.

**Прочее API:**
- `GET /profile/v2/access-requests` — свои запросы с ответами участников, фильтр `collective_id`;
- `GET /profile/v2/access-requests/{id}` — ответы участников (`person_id` и статус), только автору;
- `GET /profile/v2/access-requests/fields` — поля, которые можно запрашивать;
- `GET /profile/v2/grants/incoming` — входящие для субъекта: кто, коллектив, поля, комментарий, срок,
  статус.

Ограничение частоты создания запросов и выгрузок: в памяти процесса, на аккаунт и час
(`ACCESS_REQUESTS_PER_HOUR=10`, `ACCESS_EXPORTS_PER_HOUR=30`). При превышении —
`429 TOO_MANY_REQUESTS` с `Retry-After`.

## Замеры (раздел 11 ТЗ)

Провайдер `local`, Windows, PostgreSQL в Docker на той же машине:
- одно поле: шифрование около 21 мкс, расшифровка около 14 мкс;
- выгрузка 50 участников по 4 зашифрованных поля паспорта, сервисный слой: около 130 мс с холодным
  кэшем DEK, около 70 мс с тёплым;
- через HTTP на простаивающем монолите: около 170 мс.

Журнал и уведомления выгрузки пишутся одной пакетной вставкой каждый. Поштучные вставки давали
1,1 с на те же 50 человек. Vault в тестовой среде не поднимался, его замера нет.

## Отступления от ТЗ

- Проверка руководителя возвращает ещё название и признак «подтверждён», а не только `bool`.
  Название сохраняется в запросе (`collective_name`): в `profile` нет названий коллективов, а субъекту
  нужно знать, в каком коллективе просят. Переименование коллектива в старых запросах не отражается.
- Запрашивать данные может только руководитель подтверждённого коллектива — решение владельца.
- `profile.workplace` нельзя запрашивать (`grantable=False`) — решение владельца: у `profile` есть
  только id организации.
- Добавлены эндпоинты списка своих запросов и списка полей, которых нет в таблице раздела 10.
- В `skipped` есть статус `not_member`. Истёкший запрос не даёт «всех пропущенных как expired», а
  отказывает целиком (проверка 1 раздела 8.3).
- `sensitive_access_log.subject_person_id` стал необязательным для строки об операции целиком.
  CHECK требует тогда `request_id`. Откат миграции удаляет такие строки.
- Шаг «грант» политики `can_view` реализован только в выгрузке: ни один другой эндпоинт не отдаёт
  чужие поля.
- Отдельного индекса `access_grant (request_id)` нет: его роль играет уникальный индекс.
- Отказы субъекта в собственных действиях (охлаждение, неверный переход) не журналируются: это не
  доступ к данным. Руководитель об ответах субъектов не уведомляется.

## Принятые риски и последствия

- Ограничение частоты живёт в процессе: при нескольких воркерах оно умножается, после перезапуска
  обнуляется.
- Руководитель может создавать много запросов к одному коллективу (каждый — уведомление участникам);
  сдерживает только ограничение частоты.
- Выгрузка в браузере руководителя уже вне контроля системы. След — журнал и уведомления.
- Владелец таблиц в БД может отключить триггеры неизменяемости, как и у журнала (runbook, этап 4).
