# ADR 0006. Ротация ключей, смена провайдера и уничтожение ключа (этап 4)

Дата: 2026-11-07. Статус: принято. Основа: основное ТЗ, разделы 4.3, 5.5, 5.6, 8.5, 11, 12;
ADR 0003, 0004.

## Контекст

После этапа 3 у каждого человека один DEK. Он обёрнут KEK активного провайдера, `rotated_at` и
`destroyed_at` в `person_key` пустуют. Этап 4 даёт три операции:
- перенос DEK под новый KEK или к другому провайдеру;
- новый DEK человека с перешифровкой его данных;
- уничтожение ключа вместе с данными.

Кроме того — runbook и модель угроз.

## Решения

**Команды:** `python -m profile.manage.keys` с подкомандами `status`, `rewrap`, `rotate-dek`,
`destroy`. Логика — в `KeyMaintenanceService` (`service/key_maintenance.py`, наследник
`PersonalDataService`): шифртекст по-прежнему трогает только этот слой. Настройки пакетов —
`MIGRATION_BATCH_SIZE` (100) и `MIGRATION_SLEEP_MS` (50).

**`status`** считает DEK по `key_ref` и по версиям, а также уничтоженные. С `--retired <key_ref>`
завершается с кодом 1, пока этим ключом обёрнут хоть один DEK — это проверка «старый KEK больше не
нужен».

**`rewrap --to <провайдер>`:**
- связка: целевой провайдер оборачивает, остальные настроенные (`KEY_PROVIDER`, `KEY_PROVIDERS_READ`)
  только разворачивают;
- переносятся живые DEK, чей `key_ref` не совпадает с текущим ключом цели. Каждая пачка — отдельная
  транзакция с `FOR UPDATE`;
- данные не перешифровываются, сервис не останавливается;
- повторный запуск — продолжение или пустой проход;
- `--dry-run` только считает;
- перед первой записью — пробный wrap/unwrap всеми провайдерами;
- если ключ цели повернули во время работы, команда переходит на самую новую версию.

Это покрывает новую версию KEK (`local` v1→v2, `vault … rotate`) и смену провайдера.

**`rotate-dek`:**
- одна транзакция на человека: новый DEK версии N+1, перешифровка всех зашифрованных колонок реестра
  (таблицы и связь строки с человеком — из `Source`), замена обёртки и `rotated_at`;
- отбор: `--person` или `--older-than-days` по `rotated_at` (или `created_at`);
- «по расписанию» — тот же запуск из cron или таймера systemd: фоновых потоков в процессе нет (ТЗ 11
  для `local`);
- предел — 255 версий: столько вмещает байт версии в заголовке поля.

**Блокировки вместо хранения старых версий DEK.** ТЗ требует читать старую версию на время ротации.
Вместо таблицы версий:
- чтение берёт `person_key` с `FOR SHARE` (`_read_keys`);
- запись нового значения — `FOR UPDATE` (`_write_key`);
- ротация и уничтожение — `FOR UPDATE`.

Ротация человека ждёт текущие чтения и записи, а они ждут её. Смешанного состояния никто не видит, а
старый DEK после ротации не нужен.

**Уничтожение ключа (crypto-shredding):**
- **Как запускается** (решение владельца): эндпоинт суперпользователя
  `POST /profile/v2/persons/{id}/destroy-key` с телом `{confirm_person_id, reason}` и команда
  `destroy --person … --reason … --yes`.
- **Отказы:**
  - `confirm_person_id` не совпадает с путём → `422 DESTROY_NOT_CONFIRMED`;
  - человека нет → `404 PERSON_NOT_FOUND`;
  - живого ключа нет → `409 PERSON_KEY_ABSENT`.
- **Что происходит, одна транзакция** (решение владельца — удалять строки):
  - строки, где зашифрованное значение обязательно (`NOT NULL`), удаляются: паспорт, а каскадом и
    вариант ФИО;
  - необязательные зашифрованные значения обнуляются;
  - `wrapped_dek` и `key_ref` стираются, ставится `destroyed_at`;
  - в журнал пишется `key_destroyed` с автором: суперпользователь, а из CLI — пустой автор и
    `via=none`;
  - человеку уходит уведомление: какие поля, кто, причина, когда.
- **Новые данные** этого человека получают новый DEK следующей версии.
- **Кэш.** Эндпоинт чистит кэш DEK своего процесса. CLI не может почистить кэш сервиса: тот истекает
  через `DEK_CACHE_TTL_SEC`, а данных к тому моменту уже нет.
- **Проверка реестра при старте:** зашифрованная `NOT NULL` колонка в таблице, где строка — сам
  человек (`Source.person == Source.row`), запрещена. Иначе уничтожение ключа пришлось бы делать
  удалением человека.

**Документы:** `docs/runbook/personal-data-keys.md` и `docs/threat-model.md`.

## Приёмка

Ротация и смена провайдера прогнаны на тестовых данных
(`tests/profile/test_profile_key_maintenance.py`):
- `local` v1→v2 с удалением `kek.v1` и чтением после;
- прерванный перенос, продолженный повторным запуском;
- `local`→`vault` и поворот ключа Vault (на заглушке);
- `status --retired`;
- ротация DEK: выборочная и по возрасту;
- уничтожение через эндпоинт и CLI, отказы;
- поле из фикстуры: ротация и обнуление при уничтожении.

## Отступления от ТЗ

- Команда называется `python -m profile.manage.keys rewrap --to …`, а не `manage rewrap-keys --to …`:
  в проекте нет общей утилиты `manage`, команды — это модули (`python -m profile.bootstrap.links`).
- Старые версии DEK не хранятся: атомарную подмену обеспечивают блокировки (см. выше). Колонок и
  таблиц не добавлено.
- Ротация DEK по расписанию — внешний планировщик, а не фоновая задача сервиса.
- Причина уничтожения не хранится в журнале (там нет такой колонки, а свободный текст в журнал не
  пишется). Она есть в уведомлении человеку; в лог приложения попадает только id человека.
- При уничтожении строки удаляются, а не помечаются нечитаемыми. Поэтому прямое чтение уничтоженных
  данных отвечает «нет данных» (404 или пустой список), а не «данные уничтожены».
- Перенос между версиями Vault идёт через `decrypt` + `encrypt`, а не нативный `rewrap` Transit: так
  один путь подходит всем провайдерам. Политике сервиса хватает `encrypt` и `decrypt`.
- `system_key` (blind index), цепочка хэшей журнала и облачные провайдеры по-прежнему не делались.

## Принятые риски и последствия

- Чтения чувствительных данных берут разделяемую блокировку строки `person_key`. Это немного дороже
  и на время ротации одного человека задерживает его чтения.
- Уничтожение необратимо для живой БД, но не для бэкапов (runbook). После восстановления из бэкапа
  уничтожение нужно повторить по логам.
- Командам нужны те же настройки, что и сервису. При запуске вне контейнера пакет `profile` спорит со
  стандартным модулем `profile`: запускать из `src/` или с `PYTHONPATH`, как в образах.
