# Runbook: ключи персональных данных в `profile`

Для тех, кто обслуживает развёртывание. Устройство описано в ADR 0003–0006 и в модели угроз
(`docs/threat-model.md`).

## Что где лежит

- **DEK** — ключ данных человека, по одному на человека. Хранится в `profile.person_key` в обёрнутом
  виде: `wrapped_dek`, `key_ref` (`провайдер:имя:версия`, например `local:kek:2`), `dek_version`,
  `rotated_at`, `destroyed_at`.
- **KEK** — ключ, которым обёрнуты DEK. Он у провайдера:
  - `local`: файлы `kek.v1`, `kek.v2`, … в `LOCAL_KEK_DIR`, права 0400, владелец — пользователь сервиса.
    Активная версия задаётся `LOCAL_KEK_ACTIVE`; можно запечатать файлы паролем
    (`LOCAL_KEK_PASSPHRASE_FILE`).
  - `vault`: ключ Transit `profile-kek` (`derived=true`).
- **Связка ключей.** `KEY_PROVIDER` оборачивает новые DEK. `KEY_PROVIDERS_READ` — провайдеры, которые
  только разворачивают ключи, обёрнутые ими раньше.
- **Команды** запускаются там, где работает `profile`, с теми же настройками (база, провайдеры):

  ```bash
  python -m profile.manage.keys status [--retired local:kek:1]
  python -m profile.manage.keys rewrap --to <local|vault> [--dry-run] [--batch-size N] [--sleep-ms M]
  python -m profile.manage.keys rotate-dek [--person ID ...] [--older-than-days N] [--dry-run]
  python -m profile.manage.keys destroy --person ID --reason "..." --yes
  ```

  `rewrap` и `rotate-dek` идут пачками (`MIGRATION_BATCH_SIZE`, по умолчанию 100) с паузой
  `MIGRATION_SLEEP_MS` (50 мс). Прерванный запуск продолжается повторным запуском. Сервис при этом
  останавливать не нужно.
- **Проверка здоровья:** `GET /profile/v2/health/keys`.

## Посмотреть состояние

```bash
python -m profile.manage.keys status
```

Выводит, сколько DEK обёрнуто каждым `key_ref`, сколько ключей каждой версии и сколько уничтожено.
С `--retired <key_ref>` команда завершается с кодом 1, пока этим ключом обёрнут хоть один DEK.
Эту проверку делают перед удалением старого KEK.

## Ротация KEK, провайдер `local`

1. Создать новую версию в каталоге ключей:
   `python -m profile.crypto.keygen <LOCAL_KEK_DIR> --version N+1`. С паролем — добавить
   `--passphrase-file`.
2. Положить её в секрет платформы рядом со старой и сохранить офлайн-копию (см. «Где хранить копию
   KEK»).
3. Поставить `LOCAL_KEK_ACTIVE=N+1` и перезапустить `profile`. Новые DEK оборачиваются новой версией,
   старые по-прежнему читаются.
4. Проверить объём: `python -m profile.manage.keys rewrap --to local --dry-run`.
5. Перенести ключи: `python -m profile.manage.keys rewrap --to local`.
6. Убедиться, что старый KEK больше ничего не оборачивает:
   `python -m profile.manage.keys status --retired local:kek:N`.
7. Убрать `kek.vN` из секрета. Копию держать, пока живы бэкапы БД, сделанные до шага 5: в них
   `person_key` ещё обёрнута старой версией.

## Ротация KEK, провайдер `vault`

1. `vault write -f transit/keys/profile-kek/rotate`. Новые обёртки сразу идут новой версией,
   старые читаются.
2. `python -m profile.manage.keys rewrap --to vault`. Если ключ повернули ещё раз во время работы,
   команда сама переходит на самую новую версию.
3. Проверка: `status --retired vault:profile-kek:<старая версия>` завершается с кодом 0.
4. Поднять `min_decryption_version` ключа до новой версии. Сделать это только после того, как истекут
   бэкапы, которым нужна старая.

Политика сервиса — только `encrypt` и `decrypt` на `transit/encrypt/profile-kek` и
`transit/decrypt/profile-kek`. Ротацию ключа выполняет оператор со своей политикой, не сервис.

## Смена провайдера (например, `local` → `vault`) без остановки

1. Настроить `VAULT_*` для `profile` и добавить `vault` в `KEY_PROVIDERS_READ`
   (`KEY_PROVIDER=local`). Перезапустить: при старте сервис проверяет каждый провайдер пробной
   обёрткой.
2. `python -m profile.manage.keys rewrap --to vault`. Ключи переходят в Vault, сервис их уже читает.
3. Переключить `KEY_PROVIDER=vault`, `KEY_PROVIDERS_READ=local` и перезапустить.
4. Ещё раз выполнить `rewrap --to vault`: он переносит DEK, созданные между шагами 2 и 3.
5. `status --retired local:kek:<версия>` → код 0. После этого убрать `local` из `KEY_PROVIDERS_READ`.
   Файлы `kek.v*` хранить, пока живы бэкапы, которым они нужны.

Обратный переход и переход между версиями одного провайдера делаются так же. Данные при этом не
перешифровываются: меняется только обёртка DEK.

## Ротация DEK

Новый DEK человека (версия +1) создаётся в одной транзакции с перешифровкой всех его зашифрованных
полей. Чтения и записи данных этого человека на это время ждут блокировку, поэтому смешанного
состояния никто не видит.

- **По команде:** `python -m profile.manage.keys rotate-dek --person <id>`. Повод — подозрение на утечку
  DEK конкретного человека.
- **По расписанию.** Фоновых задач в `profile` нет (требование режима экономии), поэтому ротацию
  запускает cron или таймер systemd на хосте `profile`:

  ```cron
  30 3 * * 0  cd /srv/aef && docker compose exec -T aef python -m profile.manage.keys rotate-dek --older-than-days 365
  ```

  `aef` — в режиме монолита, в режиме микросервисов — контейнер `profile`. В образах `PYTHONPATH=/app`,
  поэтому `profile` — это пакет сервиса, а не одноимённый модуль стандартной библиотеки. При запуске
  из исходников переходить в `src/`.

- **Предел:** версия DEK хранится в одном байте заголовка поля, после 255 ротаций одного человека
  ротация отказывает.

## Уничтожение ключа человека (crypto-shredding)

- **Суперпользователь:** `POST /profile/v2/persons/{id}/destroy-key` с телом
  `{"confirm_person_id": "<тот же id>", "reason": "..."}`.
- **Оператор:** `python -m profile.manage.keys destroy --person <id> --reason "..." --yes`.

В одной транзакции:
1. Удаляются строки, где зашифрованное значение обязательно (паспорта вместе с вариантом ФИО).
   Необязательные зашифрованные значения обнуляются.
2. Стирается `wrapped_dek`, ставится `destroyed_at`.
3. В журнал пишется `key_destroyed`, человеку уходит уведомление с причиной.

Новые данные этого человека потом шифруются новым ключом.

**Остаточный риск — бэкапы.** Бэкап, снятый до уничтожения, содержит и шифртекст, и обёрнутый DEK.
Пока бэкап жив и жив KEK, которым тот DEK обёрнут, данные можно восстановить. Отсюда два правила:
- срок хранения бэкапов задаёт срок, после которого уничтожение окончательное;
- KEK удаляется по правилам ротации, а не раньше.

После восстановления БД из бэкапа:
- уничтожить ключи всех, кого уничтожали после даты бэкапа;
- список брать из логов приложения (строки «The data key of a person was destroyed: <id>»,
  логи хранятся вне БД) или из `sensitive_access_log` более нового бэкапа.

Сервисный процесс держит DEK в кэше не дольше `DEK_CACHE_TTL_SEC` (60 с). Уничтожение через эндпоинт
чистит этот кэш сразу, через CLI — по истечении срока (данных к тому моменту уже нет).

## Потеря KEK

- Без KEK обёрнутые им DEK не развернуть: зашифрованные поля этих людей потеряны. Сервис отвечает
  `503 PERSONAL_DATA_UNAVAILABLE` на их чтение, а `GET /profile/v2/health/keys` — `503`, если не
  работает сам провайдер.
- Восстановить ключ из офлайн-копии и перезапустить `profile`.
- Если копии нет: поставить новый KEK и уничтожить ключи затронутых людей (`destroy`), чтобы снять
  ошибки чтения. Сообщить людям, что паспортные данные нужно ввести заново.

## Компрометация KEK

1. Создать новую версию KEK или повернуть ключ Vault и сделать её активной.
2. `rewrap` на новую версию, затем `status --retired <скомпрометированный>` → код 0.
3. `rotate-dek` для всех: `--older-than-days 0` или без фильтра. С утёкшим KEK и дампом БД можно
   развернуть старые DEK, а ротация делает их бесполезными для новых данных. Данные из уже утёкшего
   дампа всё равно скомпрометированы.
4. Отозвать старую версию: удалить файл или поднять `min_decryption_version`. Секреты доступа к
   провайдеру (AppRole `secret_id`, токены) перевыпустить.
5. Оценить по журналу (`sensitive_access_log`), что могло утечь, и решить вопрос об уведомлении людей.

## Подозрение на компрометацию процесса `profile` или его хоста

Скомпрометированный процесс видит расшифрованные данные и DEK в памяти и может попросить провайдер
развернуть любой ключ. От этого шифрование не защищает (см. модель угроз).

1. Изолировать хост, остановить `profile`, сохранить логи.
2. Перевыпустить всё, что было у процесса:
   - `kek.v*`: новая версия, плюс `rewrap`;
   - секреты Vault;
   - пару `PROFILE_RSA_*`;
   - пароль БД.
3. `rotate-dek` для всех.
4. Разобрать журнал доступа за период и уведомить затронутых людей.

## Где хранить копию KEK

- Отдельно от бэкапов БД: офлайн-носитель в сейфе или менеджер секретов с другими администраторами.
  Бэкап БД вместе с KEK — это открытые данные.
- Копия нужна для каждой версии, пока на неё ссылается хоть один живой бэкап.
- С паролем (`LOCAL_KEK_PASSPHRASE_FILE`) копию файла можно держать ближе, а пароль — отдельно.

## Новое чувствительное поле

1. **Запись в реестре** (`profile/registry/fields.py`):
   - ключ, название, колонки, `encrypted=True`;
   - `Source` для новой таблицы — как строка доходит до человека.

   `validate_registry()` при старте проверяет запись:
   - колонка `bytea`;
   - у таблицы есть источник;
   - зашифрованная колонка в таблице, где строка — сам человек, обязана быть `NULL`-допустимой (иначе
     уничтожение ключа пришлось бы делать удалением человека).
2. **Колонка пуста — одна миграция.** Пересоздать колонку как `bytea` (`NOT NULL` сохраняется). Сначала
   миграция проверяет, что значений нет, иначе падает (образец — `b7d4e9a1c3f6_encrypt_passport.py`).
3. **В колонке уже есть данные — expand → migrate → contract:**
   - **expand.** Добавить зашифрованную колонку рядом с открытой и выложить код, который пишет в обе
     (запись через `PersonalDataService._seal`).
   - **migrate.** Идемпотентный пакетный скрипт: читает открытое значение, шифрует, пишет в новую
     колонку. Отмечает прогресс (обработанные id), сверяет расшифрованное с исходным и продолжается с
     места остановки. Пачки и пауза — `MIGRATION_BATCH_SIZE`, `MIGRATION_SLEEP_MS`.
   - **contract.** Снять бэкап, переключить чтение на зашифрованную колонку, удалить открытую.
     Помнить, что старые бэкапы содержат открытое значение.
4. **Тесты** параметризованы по реестру. Фикстура `secret_note` показывает весь путь нового поля без
   правок слоя: шифрование, чтение, запрос доступа, выгрузка, ротация, уничтожение.

## Роль БД для приложения

Журналы и история (`sensitive_access_log`, `person_account_history`,
`person_field_visibility_history`, `access_request`, `access_request_field`) защищены триггерами
`append_only_guard()`. Владелец таблицы может отключить триггер, поэтому приложение не должно быть
владельцем:

```sql
CREATE ROLE profile_owner NOLOGIN;      -- владелец схемы, от его имени идут миграции
CREATE ROLE profile_app LOGIN PASSWORD '...';
ALTER TABLE ... OWNER TO profile_owner; -- для каждой таблицы
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO profile_app;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO profile_app;
```

Миграции запускаются под `profile_owner` (через `SET ROLE` или отдельное подключение), сервис — под
`profile_app`.

## Хранение журнала доступа

- **Срок.** `sensitive_access_log` растёт с каждым чтением, свои чтения тоже пишутся. Рекомендуемый
  срок — 3 года (уточнить с юристом), записи `key_destroyed` и `denied` — дольше.
- **Партиционирование** при росте: секции по месяцам `created_at` (декларативное
  `PARTITION BY RANGE`). Новую таблицу создать миграцией, перенести данные, повесить те же триггеры на
  каждую секцию. Старая секция удаляется `DROP` или `DETACH` от имени владельца — это и есть
  применение срока хранения.
- **Без партиций** удаление старых строк делает только владелец таблицы:
  `ALTER TABLE ... DISABLE TRIGGER sensitive_access_log_rows`, `DELETE ... WHERE created_at < ...`,
  `ENABLE TRIGGER`. Выполнять одной транзакцией и записывать в журнал изменений инфраструктуры.
